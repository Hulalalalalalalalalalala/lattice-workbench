# messagetag

命令行认证标签工具，提供：

- `--version`：版本查询；
- `tag`：使用自己提供的密钥，对消息文件的完整内容计算 HMAC-SHA-256 认证标签；
- `verify`：用同一把密钥，确认消息文件的完整内容是否与一个已有标签一致。

## 依赖

- 支持 C++20 的编译器（CMake 构建中关闭了编译器扩展）；
- CMake 3.20 或更高版本；
- OpenSSL（使用其 `libcrypto` 中的标准 HMAC/SHA-256 实现，需 OpenSSL 1.1.1 及以上，OpenSSL 3.x 亦可）。

Debian/Ubuntu 上可通过 `sudo apt install libssl-dev` 安装开发文件。若 OpenSSL 不在标准搜索路径，可在配置时指定：

```sh
cmake -S . -B build -DOPENSSL_ROOT_DIR=/path/to/openssl/prefix
```

## 构建与运行

```sh
cmake -S . -B build
cmake --build build
./build/messagetag --version
```

输出版本号并以退出码 0 结束：

```text
messagetag 0.1.0
```

## 生成认证标签

```sh
messagetag tag --key-hex <十六进制密钥> --file <消息文件路径>
```

### 密钥的表示

- `--key-hex` 表达的是**原始密钥字节**：每两位十六进制字符对应一个字节，大小写字母均接受。
- 开头的零必须保留。例如 `0001` 表示两个字节 `00 01`，不会被当作数值 `1`，也不会把字符 `"0001"` 本身作为密钥。
- 密钥必须非空，且字符数为偶数，只接受数字与字母 `a-f`/`A-F`；不接受 `0x` 前缀，也不接受夹带的空白字符。
- 不符合以上规则时按参数错误处理，不会产生认证标签；错误信息也不会回显密钥内容。

### 消息文件按字节处理

- 消息取自文件中的**全部原始字节**，不作文本解释：不去掉末尾换行、不转换换行形式、不忽略零字节。
- 空文件是合法消息，仍会生成标准 HMAC-SHA-256 标签。
- 文件路径只用于定位输入，不参与认证：相同密钥、相同文件内容放在不同路径下会得到相同标签。

### 从标准输入读取消息（`--file -`）

`--file` 的值恰好是单个减号 `-` 时，消息改从**标准输入**读取：直到输入正常结束（EOF）为止到达的全部字节作为一条消息认证，不必先保存临时文件：

```sh
printf 'hello\n' | ./build/messagetag tag --key-hex 0001 --file -
```

输出与对同内容文件生成的标签完全相同（同一密钥、同一串字节，无论来自文件还是标准输入，标签一致）：

```text
307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5d
```

- 字节规则与文件输入一致：空输入是合法消息（如 `: | messagetag tag ... --file -` 或重定向自 `/dev/null`），零字节及其后的内容、末尾换行、不同换行形式都参与认证；不裁剪、不转换，也不把某一行结束当作整条消息结束。输入分几次到达不影响结果。
- 消息可以很大：处理时只使用固定大小的缓冲区，内存占用不随消息总长度增长。
- 输入尚未结束时不会提前输出标签，也不会输出等待输入的提示；正常结束后仍只输出 64 个小写十六进制字符加换行，退出码 0。
- 参数错误（非法密钥、缺少必需参数、不认识的参数等）仍在**读取标准输入之前**以退出码 2 报告原因和用法——即使上游一直不结束，命令也不会空等消息。
- 标准输入无法读取，或读到非空前段后发生读取错误时，以退出码 1 结束，标准输出为空，标准错误明确说明标准输入读取失败；已经收到的前段不会被当成完整消息给出认证结论。
- 只有 `--file` 的值**恰好**是 `-` 时才读取标准输入；若确有名为 `-` 的文件，用 `./-` 或完整路径指定，仍按普通文件读取。

verify 同样支持 `--file -`，待验证标签继续通过 `--tag-hex` 提供：

```sh
printf 'hello\n' | ./build/messagetag verify --key-hex 0001 --file - \
    --tag-hex 307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5d
# 标准输出: OK
# 退出码: 0
```

验证的输出与退出码含义与文件输入完全相同（通过输出 `OK` 退出码 0，不匹配退出码 3 且标准输出为空，读取失败退出码 1，参数错误退出码 2 且先于读取标准输入报告）。

### 输出与退出码

成功时，标准输出只包含一行由 **64 个小写十六进制字符**组成的标签，以换行结束，退出码为 `0`，可以直接保存或交给其他程序处理：

```text
307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5d
```

只有这一整行（64 个字符加末尾换行）**完整写入标准输出并完成缓冲刷新**之后，命令才以退出码 `0` 结束。标签本身计算正确并不等于输出成功：

| 情况 | 标准错误 | 标准输出 | 退出码 |
| --- | --- | --- | --- |
| 成功（整行已完整写入并刷新） | 无 | 标签（一行） | `0` |
| 标准输出无法完整写入结果行（目标空间耗尽、写入设备报错、管道读取端已关闭等） | 一条“标准输出写入失败”说明（见下） | 不保证完整；已送出的残留字节不构成标签 | `1` |
| 文件无法打开或读取失败 | 读取失败说明 | 无任何输出 | `1` |
| 缺少必需参数、选项缺少值、密钥格式错误、存在不认识的参数 | 明确原因及该命令用法 | 无任何输出 | `2` |

当标准输出因为目标空间耗尽（ENOSPC）、写入设备报错（如 EIO）或管道读取端已经关闭（EPIPE）而无法写完结果行时——无论失败发生在整行进入缓冲之后，还是已经写出部分字符——命令都以退出码 `1` 结束，且在标准错误给出**唯一一条**说明，明确指出失败发生在结果输出阶段（“standard output write failed”，并附系统错误原因）：不附带命令用法，也不再输出成功提示，更不会回显密钥。为避免被 `SIGPIPE` 直接终止，程序会在写入阶段忽略该信号，使管道关闭统一表现为退出码 `1`，而不是由信号终止。失败时此前已经交给接收方的部分字节无法撤回，但它们既不是可用标签，也不能作为输出成功的证明；调用方应以退出码 `1` 为准丢弃这些残留字节。参数格式错误、文件无法打开或读取中途失败、认证计算失败等错误优先于输出处理，其退出码与说明不受标准输出是否可写影响。


需要值的选项后面如果已经没有参数，或者紧接着的是本命令认可的某个选项名（包括同名选项，如 `--file --file`），都视为该选项缺少值，按参数错误处理，不会把后一个选项消耗成前一个选项的值。只有与选项名**完全相同**的参数才触发这一判断：其他以短横线开头的名字（如 `--notes`）仍按文件路径处理；若文件确实名为某个选项（如 `--file`），可用 `./--file` 或完整路径明确指定。显式传入的空字符串仍是“已填值”：空密钥按密钥格式错误处理，空文件路径按读取失败处理，与漏填值不同。

## 示例

密钥为两个字节 `00 01`（写作 `0001`，前导零有意义），消息文件内容为 `hello` 加一个换行符，共 6 个字节：

```sh
printf 'hello\n' > msg.txt
./build/messagetag tag --key-hex 0001 --file msg.txt
```

输出：

```text
307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5d
```

注意末尾换行属于消息的一部分；若文件内容是不带换行的 `hello`，得到的标签会不同。

## 密钥等价：不同写法的密钥可能生成相同标签

`tag` 与 `verify` 都通过 `--key-hex` 接收密钥，认证遵循标准 HMAC-SHA-256 规则。该规则允许**两种不同的密钥写法对同一消息生成相同标签、并能互相验证**。遇到这种现象时，先对照本节判断它是否属于规则允许的正常结果，而不是把密钥输入方式理解错了。本节所有长度都按 `--key-hex` 十六进制解码后的**原始字节**计数（每两位十六进制字符对应一个字节）。

### 尾部补零（补完后总长度不超过 64 字节）

HMAC-SHA-256 内部把密钥补齐到 64 字节的分组长度。因此，**非空**密钥在**尾部**追加一个或多个零字节，只要追加后的总长度仍不超过 64 字节，对同一消息的标签保持不变：例如 `ab`（1 个字节）与 `ab00`（2 个字节 `ab 00`）是等价密钥，用其中一种写法生成的标签，可以用另一种写法通过 `verify` 验证。

- 这**不是**“忽略所有零字节”：开头和中间的零字节仍然是密钥输入的一部分。`00ab` 与 `ab` 标签不同；`ab00` 只是恰好与 `ab` 等价。
- 补零有长度上限。63 字节的密钥补一个零字节到 64 字节，标签不变；但 64 字节的密钥再补一个零字节就成为 65 字节密钥，落入下一条“超长密钥”规则，标签会改变。不要把尾部补零理解成可以无限制地追加。

### 超过 64 字节的密钥

密钥超过 64 字节时，HMAC-SHA-256 先计算它的 SHA-256 摘要，再用这个 32 字节的摘要作为实际密钥。因此：**一把超过 64 字节的密钥，与把它的 SHA-256 摘要作为 32 个原始密钥字节输入，具有完全相同的认证行为**——同一消息标签相同，可以互相验证。

- 摘要写作 64 个十六进制字符，**直接交给 `--key-hex`** 即可（它就是 32 个原始密钥字节的十六进制写法）；不要把这 64 个字符本身当成 64 个密钥字节，那等于换了一把密钥。
- **恰好 64 字节的密钥不适用这一等价**：64 字节密钥原样参与认证，不会被替换成摘要。不要对所有密钥都先取 SHA-256 摘要再使用——只有超过 64 字节的密钥才存在这种等价写法。
- 空密钥依然是参数错误（退出码 2）：补零说明针对的是**非空**密钥，不意味着空输入被补零后变成合法密钥。

### 完整示例

消息文件内容为 `hello` 加一个末尾换行符，共 6 个字节（末尾换行属于消息的一部分）：

```sh
printf 'hello\n' > msg.txt
```

写法一：密钥 `ab`，即 1 个原始字节 `ab`：

```sh
./build/messagetag tag --key-hex ab --file msg.txt
```

写法二：密钥 `ab00`，即 2 个原始字节 `ab 00`（尾部补了一个零字节，总长 2 字节，不超过 64 字节）：

```sh
./build/messagetag tag --key-hex ab00 --file msg.txt
```

两种写法输出同一个标签：

```text
451dd47a1c1829d7729f65748bd7e5e83770725336d96aeee0c7ad1066aa921a
```

用写法二的密钥验证写法一生成的标签，输出 `OK` 并以退出码 0 结束：

```sh
./build/messagetag verify --key-hex ab00 --file msg.txt \
    --tag-hex 451dd47a1c1829d7729f65748bd7e5e83770725336d96aeee0c7ad1066aa921a
# 标准输出: OK
# 退出码: 0
```

超长密钥同理：65 字节的密钥 `aa` 重复 65 次（130 个十六进制字符），与它的 SHA-256 摘要 `dccc2bab3a78a627227011244bf6f6650d8ab5a3f286883ac09b9e0ba010a2a3` 作为 `--key-hex` 输入时，对上述同一消息给出同一标签 `cda078fa1af6c953f705da5b311e64004d74d8ecd9ed4ecbb7c39517358171f6`，交叉验证同样输出 `OK`、退出码 0。

### 等价不等于相同，不匹配也不等于密钥错误

- 标签相同或验证通过，**不能证明两次使用的密钥字节完全相同**——它们可能只是按上述规则等价。
- 反过来，认证不匹配（退出码 3）也**不能单独判定是密钥写错**：消息或标签不一致同样会导致不匹配。
- 密钥等价是 HMAC-SHA-256 规则允许的正常结果，**不是认证失败**：程序不会因此额外报警，输出格式与退出码跟使用同一把密钥时完全一致。

## 验证认证标签

```sh
messagetag verify --key-hex <十六进制密钥> --file <消息文件路径> --tag-hex <待验证标签>
```

`--tag-hex` 直接接受 `messagetag tag` 的输出**去掉末尾换行**后的结果——不引入任何新的标签封装格式。典型用法是先取出标签行再验证：

```sh
./build/messagetag tag --key-hex 0001 --file msg.txt > msg.tag
TAG=$(cat msg.tag)          # 命令替换会去掉末尾换行
./build/messagetag verify --key-hex 0001 --file msg.txt --tag-hex "$TAG"
```

verify 本身不会替调用方裁剪空白：带末尾换行或夹带空格的标签按参数错误处理。

### 待验证标签的格式

- 必须恰好表示 **32 个字节，即 64 个十六进制字符**，大小写字母均接受。
- 空值、截短或超长标签、非十六进制字符、夹带的空白以及 `0x` 前缀都属于参数错误。
- 密钥继续遵守与 `tag` 相同的规则：非空、偶数长度、保留前导零字节。
- **输入格式先于文件读取检查**：即使文件不存在，非法标签或密钥报告的也是参数错误（退出码 2），而不是读取失败或不匹配。

### 输出与退出码

| 情况 | 标准错误 | 标准输出 | 退出码 |
| --- | --- | --- | --- |
| 验证通过（整行 `OK\n` 已完整写入并刷新） | 无 | `OK`（一行，以换行结束） | `0` |
| 标准输出无法完整写入结果行（目标空间耗尽、写入设备报错、管道读取端已关闭等） | 一条“标准输出写入失败”说明 | 不保证完整；残留字节不构成验证通过的证明 | `1` |
| 认证标签不匹配 | 明确说明认证标签不匹配 | 无任何字节 | `3` |
| 文件无法打开或读取失败、认证计算失败 | 读取/计算失败说明 | 无任何输出 | `1` |
| 缺少必需参数、选项没有值、未知参数、密钥或标签格式错误 | 明确原因及 `verify` 命令用法 | 无任何输出 | `2` |

只有整行 `OK\n` **完整写入标准输出并完成缓冲刷新**之后，verify 才以退出码 `0` 结束；认证比较通过本身不能替代输出成功。标准输出因目标空间耗尽、写入设备报错或管道读取端已关闭（程序在写入阶段忽略 `SIGPIPE`，管道关闭因此统一表现为退出码 `1` 而非被信号终止）而无法写完结果行时，无论此前是否已写出部分字符，都以退出码 `1` 结束，并在标准错误给出**唯一一条**指向结果输出阶段的“standard output write failed”说明（附系统错误原因）：不附带命令用法、不再输出成功提示，也不回显密钥、待验证标签或重新计算出的标签。已经送出的残留字节无法撤回，但不构成“验证通过”的证据，调用方应以退出码 `1` 为准。参数格式错误、文件无法打开或读取中途失败、认证计算失败以及标签不匹配优先于输出处理，其退出码与说明不受标准输出是否可写影响。

“选项没有值”的判定与 `tag` 相同：选项后面没有参数，或紧接着的是 `verify` 认可的某个选项名（含同名选项），都按缺少值处理并在读取文件之前报告；只有与选项名完全相同的参数才触发，其他以短横线开头的路径不受影响，显式空字符串仍按各自的格式/读取错误处理。

验证通过时标准输出只有一行 `OK` 加换行，适合直接在脚本中按退出码判断：

```sh
if ./build/messagetag verify --key-hex 0001 --file msg.txt --tag-hex "$TAG"; then
    echo "authenticated"
fi
```

不匹配（退出码 3）的含义仅仅是“给定密钥、文件内容与标签三者不一致”：**修改消息内容或换用另一把密钥都可能得到这一结果**，程序不会断言一定是消息被改动、密钥错误还是标签本身有误。错误信息不会输出重新计算的标签、与待验证标签相匹配的前缀，也不会回显密钥内容；标签比较对全部 32 个字节进行，耗时不取决于匹配前缀的长度，不暴露逐段匹配的信息。

消息文件与 `tag` 一样按**全部原始字节**认证：空文件是合法消息，零字节及其后的内容、末尾换行都参与验证，文件路径不参与认证。若文件打开成功但读取中途失败，已读入的前段不会被当成完整消息给出“通过”或“不匹配”的结论，而是按读取失败（退出码 1）处理。

### 示例

沿用 `tag` 一节的消息（内容为 `hello\n`，密钥字节 `00 01`）：

```sh
printf 'hello\n' > msg.txt
TAG=307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5d
./build/messagetag verify --key-hex 0001 --file msg.txt --tag-hex "$TAG"
# 标准输出: OK
# 退出码: 0
```

把标签末位换掉（代表消息、密钥或标签中任意一处不一致）：

```sh
./build/messagetag verify --key-hex 0001 --file msg.txt \
    --tag-hex 307a25cbcb6cbca48f5dd2b05fd9174c0cf17580f4ea8dd667092f11a77b4d5c
# 标准输出为空；标准错误说明认证标签不匹配
# 退出码: 3
```

标签少一个字符则是参数错误，与文件是否存在无关：

```sh
./build/messagetag verify --key-hex 0001 --file msg.txt --tag-hex "${TAG%?}"
# 标准输出为空；标准错误给出原因与 verify 用法
# 退出码: 2
```

也可直接运行：`python3 tests/regression_test.py ./build/messagetag [read 垫片] [write 垫片]`（后两个参数可省略，省略时脚本会在可执行文件旁查找垫片，找不到则现场编译或跳过相应用例）。

期望值不取自本程序自己的输出，而是有两个相互独立的确定依据：

- [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231.html) 第 4 节公布的 HMAC-SHA-256 标准向量，其中包含 **131 字节、超过 SHA-256 的 64 字节块大小**的密钥用例；
- Python 标准库 `hmac`/`hashlib` 在测试运行时重新计算的结果，并与测试中硬编码的常量再次比对。

测试覆盖：空文件、含零字节且零字节后仍有内容的消息、LF/CR/CRLF 不互相转换、带不带末尾换行分别对应不同标签、长度为 131195 字节（超过 64 KiB 且不是 64 KiB 整数倍）的文件且首/中/尾字节改动都能被发现、长度恰好为 64 KiB 整数倍（1 倍、2 倍、3 倍）的文件按全部原始字节得到独立计算的标准标签（最后一次零字节读取是正常结束，最后一块既不重复也不遗漏，边界两侧各差一字节的文件标签都被固定）、相同内容在不同路径下标签一致、密钥十六进制大小写等价、前导零字节保留（包括超长密钥的情形）；并检查成功时标准输出恰为 64 个小写十六进制字符加一个换行、标准错误为空、退出码为 0，奇数长度/非十六进制密钥以退出码 2 结束且不回显密钥，文件无法打开以退出码 1 结束且不输出任何标签；`--version` 的既有行为也保持固定。

`verify` 的测试固定：验证通过时标准输出恰为 `OK\n`、标准错误为空、退出码 0，且直接接受 `tag` 输出去掉末尾换行后的标签（大小写均接受，不引入新封装）；改动消息（含仅差一个末尾换行）、换用另一把密钥、翻转标签首/中/尾字节都得到退出码 3、标准输出零字节，错误信息只说明认证标签不匹配、不归因于消息或密钥、不含重算标签或密钥；空值、截短/超长标签、非十六进制字符、空白、`0x` 前缀以及缺少必需选项、选项没有值、未知参数均以退出码 2 结束并给出原因与 `verify` 用法，且格式检查先于文件读取（文件不存在时非法标签仍报参数错误）；空文件与不同路径同样按全部原始字节认证。

`--file -`（标准输入）的测试固定：经管道送入的字节得到与同内容文件相同的独立计算标签（含空输入、零字节、各种换行形式、跨读取块的大消息与块长整数倍消息）；分几次到达的输入与一次到达结果一致，且输入未结束时进程不输出任何字节、不给出结论；名为 `-` 的文件仍可通过 `./-` 读取，而同一目录下 `--file -` 依然读标准输入；非法密钥、非法标签、缺少必需参数在上游不结束输入时也立即以退出码 2 报告，不空等消息；标准输入完全不可读（以目录作为 fd 0）以及读到非空前段后读取失败（用 read 故障垫片、把消息文件作为 fd 0 注入）都以退出码 1 结束、标准输出为空、标准错误明确说明标准输入读取失败——已收到的前段不会被当成完整消息，`tag` 不输出前段标签，`verify` 对整段标签不报不匹配、对前段标签也不报通过。

此外，回归测试通过 CMake 构建的 LD_PRELOAD 故障注入垫片（`tests/read_fault_shim.cpp`，仅用于测试，不链接进 messagetag）模拟“文件打开成功、已读入非空前段、随后读取失败”的情形：此时整次操作必须以退出码 1 结束、标准输出没有任何字节、标准错误说明读取失败——对 `tag` 而言即使已读入的前段本身能算出合法标签也不允许输出，对 `verify` 而言无论待验证标签对应整段消息还是仅对应已读前段，都不允许给出“通过”或“不匹配”的结论。该覆盖不依赖文件权限或特殊文件。直接运行测试脚本而未经过 CMake 时，脚本会在可执行文件旁查找该垫片，找不到则尝试用系统 C++ 编译器现场编译，再不行则明确跳过该用例。

read 垫片的**脚本模式**（`MESSAGETAG_READ_FAULT_SCRIPT`）还固定了与永久失败相对的**可恢复读取中断**：脚本按步描述每次对标准输入（默认 fd 0）的 `read` 行为——本次最多交付 N 字节（有界短读）、本次以 EINTR 失败（调用方应原样重试）、本次透传（`PASS`）、或自此以 EPIPE/ENOSPC/EIO 永久失败——并把每次拦截（`D<n>`/`E<n>`/`P<n>`）追加到跟踪文件，使测试能逐次证明中断确实按序注入、且发生在真正的 `read` 系统调用上，而不是用单纯延迟发送或分批发送代替。覆盖包括：尚未读到任何消息字节（空输入时连 EOF 读也包含在内）就被 EINTR 一次或连续有限次中断；已读到非空前段后被中断一次或连续多次，随后恢复读取且后续字节仍分批到达，消息含零字节及其后的内容并跨越 64 KiB 读取边界（中断点同时落在零字节附近与整块边界上）。这些情况下已收到的内容不得丢失、重复或乱序：输入正常结束后 `tag` 以退出码 0 输出 64 个小写十六进制字符加换行、标准错误为空，标签与同一密钥对未受中断的完整字节消息独立计算出的结果一致；`verify` 对完整消息的正确标签输出 `OK\n` 并退出 0，对只匹配中断前已读前段的标签仍按不匹配处理（退出 3、标准输出为空）；输入仍未结束时两个命令都不得给出任何结论或提示、也不得因中断提前结束（另有一个真实管道用例在子进程存活期间等待跟踪出现 EINTR 记录来证明这一点）。空输入在经历中断后正常结束，仍按合法空消息处理。而恢复之后若再遇永久读取错误，则维持失败含义：两个命令都退出 1、标准输出为空、标准错误说明标准输入读取失败；即使给出的标签恰好匹配此前已读的前段（含此前一字节未读时匹配空消息的标签），`verify` 也既不输出通过也不报告不匹配，诊断不回显密钥、待验证标签或重算标签。

针对**结果输出**，另有一个同构的写入故障垫片（`tests/write_fault_shim.cpp`，同样仅用于测试、不链接进 messagetag）：它让标准输出先接收指定数量的字节、随后的 `write` 以选定 errno（EPIPE/ENOSPC/EIO）失败，从而确定性地覆盖“整行已进入写出过程、但只写出了部分字符”的各个边界（0 字节、中间任意位置、差末尾换行一字节）。此时两个命令都必须以退出码 1 结束，标准输出上只允许出现已被接收的前缀（不构成完整标签行、不带末尾换行），标准错误只有一行“standard output write failed”说明，不附用法、不回显密钥或标签；而当整行（标签 65 字节、`OK\n` 3 字节）被完整接收时仍是退出码 0、标准错误为空。另有一个真实管道用例：先把管道写满使进程阻塞在写出上，再在其阻塞期间关闭唯一读取端，要求进程以退出码 1 与上述诊断结束，而不是被 `SIGPIPE` 终止（不会出现 141/负状态）或误报 0。最后还固定了错误优先级：在标准输出不可写时，参数错误（2）、读取失败（1）与标签不匹配（3）仍保持各自原有的退出码与说明，不被输出失败覆盖。

与永久失败相对的**可恢复中断**也被固定：垫片的脚本模式（`MESSAGETAG_WRITE_FAULT_SCRIPT`）按步描述每次 `write` 的行为——本次只接收 N 字节（短写）、本次以 EINTR 失败（调用方应重试）、或自此以 EPIPE/ENOSPC/EIO 永久失败——并把每次拦截追加到跟踪文件，使测试能证明中断确实按序注入而非垫片未生效。覆盖包括：尚未送出任何字节时被 EINTR 中断、已送出非空前段后被中断、多次短写与有限次 EINTR 交错后恢复，以及 64 个标签字符（或 `OK`）已送出、只剩末尾换行时被中断——这些情况下两个命令都必须仍以退出码 0 结束，标准输出恰好是完整结果行一次（已接收前段不重复、次序不变、末尾换行不缺失），标准错误为空；而可恢复步骤之后若再遇永久错误，则维持原有失败含义：退出码 1、标准输出只保留实际送出的前段、标准错误仅一条输出失败说明。
